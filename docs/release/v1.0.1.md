# incremental-lang v1.0.1: precise guarantees

**Documentation patch.** No change to the library code or its behaviour. The
public API is unchanged.

## Changed

### The fresh-parse guarantee states its condition

The README and crate docs said the tree after an edit is *always* the tree a
parse from scratch would produce. The document checks every part of the
grammar contract that it can observe from a single reparse, and widens the
reparse when a check fails. Two rules cannot be observed that way:

- the lexer looks at most one character past each token;
- no parse decision outside a reparsable node depends on that node's contents
  beyond its first token.

A grammar that breaks either can end up with a tree that differs from a fresh
parse, with no error. The detailed contract on `Grammar` already said this; the
README, the crate docs, the `Document` rustdoc and the overview in
`docs/API.md` now say it too. The crate docs also warn that a lexer which scans
ahead and then backs off, such as a table-driven maximal-munch lexer with a
fallback token, breaks the lookahead rule, and that such a lexer should mark no
kind reparsable.

### Edit cost is described precisely

The README said incremental reparsing costs time in proportion to the edit, and
that an edit's cost does not grow with the size of the file. The lexing and
parsing work is in proportion to the node around the edit. Three smaller costs
are not:

- updating the text is a `String` splice, a `memmove` of the text after the
  edit;
- finding the node scans the children of each level up to the edit, so one very
  wide level adds that scan to every edit beneath it;
- an edit made while a snapshot is held copies the child arrays on its path, in
  proportion to their widths.

The README and docs now list them.

## Upgrading

```toml
[dependencies]
incremental-lang = "1.0"
```

No code changes are needed.
