# incremental-lang v1.0.0 — API Freeze

**The surface is now stable.** v1.0.0 freezes the public API introduced in 0.2.0
under Semantic Versioning and completes the roadmap. Before the freeze, an
adversarial review tested the crate's central promise — that the tree after
every edit equals a fresh parse — against grammars written to the documented
contract. It found two places where the contract's wording promised more than
the engine can guarantee, plus one performance bug; the contract now says
exactly what a grammar must do, and the code fixes are in. The API is
unchanged from 0.2.0.

## What is incremental-lang?

The reparsing core an editor or language server needs: a document keeps a
source text and its lossless concrete syntax tree in step under edits,
rebuilding only the innermost node around each change that can safely be
reparsed on its own. A language supplies a
[`Grammar`](https://docs.rs/incremental-lang/latest/incremental_lang/trait.Grammar.html)
— a lexer and a recursive-descent parser written against
[`Builder`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Builder.html)
— and a
[`Document`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Document.html)
does the rest, reporting each edit as a
[`Reparse`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Reparse.html)
and its running work as
[`Stats`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Stats.html).
The tree is an `Arc`-shared
[`Tree`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Tree.html)
read through positioned
[`Node`](https://docs.rs/incremental-lang/latest/incremental_lang/struct.Node.html)
and
[`Element`](https://docs.rs/incremental-lang/latest/incremental_lang/enum.Element.html)
views, `O(1)` to snapshot and safe to send to another thread. It is
`#![forbid(unsafe_code)]`, `no_std`-compatible, and built on `syntax-lang`.

## The stability promise

As of 1.0.0 the public API is frozen. Within the `1.x` series:

- The surface will not change in a breaking way. A breaking change means a new
  major version.
- The **equivalence guarantee** is the contract: for a grammar that meets the
  lexer and parser contracts, the tree after every successful edit equals the
  tree `Document::new` produces from the new text. Which node an edit rebuilds
  is an optimization — `Reparse::span` always covers everything that changed,
  but how small it is may improve.
- The **grammar contract** will not grow: a grammar that meets it under 1.0
  meets it under every 1.x. The document's checks may become stricter or
  smarter, never looser.
- The **builder semantics** are fixed: what counts as significant, where
  trivia is placed, losslessness whatever the grammar does, and that looking
  past the end of a node being reparsed refuses the reparse.
- **Edits are transactional**: a refused edit, or a caught panic in grammar
  code, leaves text, tree, and statistics unchanged.
- The meaning of every `Stats` field and `Error` variant is fixed; both types
  are `#[non_exhaustive]`, so counters and failure modes can be added in a
  minor release.
- `syntax-lang` 1 is a public dependency (the `Span`, `Token`, and `TokenKind`
  re-exports and `Tree::to_syntax`).
- MSRV (Rust 1.85) is a compatibility surface: raising it is a documented
  minor change, never a patch.

Not promised: `Display` wording, `Debug` output, the tree's internal
representation, which node a given edit rebuilds, the `Stats` counts for a
given edit sequence, and performance figures.

## What changed in 1.0.0

### The grammar contract, stated precisely

Two rules that single-node reparsing relies on were missing or misstated, and
grammars written to the old wording could produce an incremental tree that
differs from a fresh parse:

- **A lexer may look at most one character past each token.** The old text
  said any longest-match lexer qualifies, but one that scans ahead and backs
  off — matching `"…"` to a closing quote and falling back to a lone `"` when
  there is none — lets a quote typed late in a line change how text far
  before it lexes, beyond the window the document relexes. Unterminated
  literals should run to the end of the line or input instead, as the bundled
  JSON grammar's do.
- **Nothing outside a reparsable node may depend on its contents beyond its
  first token.** The old text constrained the node's own parse and the
  decision to start it, but not lookahead from the surrounding parse past the
  node's first token, or results its parse feeds back (an element count
  deciding what follows).

Neither can be observed from a single reparse, so they are now listed as the
grammar's responsibility, next to the checks the document does make, with the
advice to hold a grammar's incremental trees to fresh parses in a property
test.

### Fixed

- **Deep nesting no longer makes edits quadratic.** An edit beneath a long
  chain of non-reparsable nodes (a left-associative operator chain, say)
  walked down from the root once per level. Each level's facts are now
  recorded on one walk down; 40,000 levels went from seconds per edit to
  under half a millisecond.
- **`start_at` keeps trivia outside.** A node opened at a checkpoint taken
  after the last consumed token could begin with the trivia before its first
  token. It now places that trivia outside, as `start` does.
- **A caught grammar panic leaves the counters alone.** Work done on a
  single-node attempt is committed to `Stats` only when the edit succeeds.

The `edit_deep` benchmark and regression tests cover all three.

### What held up

The review's fuzzing of a contract-compliant grammar that exercises every
builder feature — empty nodes at node edges, zero-width tokens and markers,
comments, checkpoints, multi-byte text — ran about five million edits without
a divergence, and found no input that makes library code panic or overflow,
and no refused edit that changes the document.

## Breaking changes

**None.** The API is identical to 0.2.0. The contract clarifications describe
what was always required for incremental results to match fresh parses; a
grammar that met them before is unaffected.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu, from a sibling-free copy, as CI
checks the crate out), Rust stable and the 1.85 MSRV; the same commands run in
the configured CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
cargo test
cargo test --all-features
cargo test --no-default-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo build --examples
cargo +1.85 test --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo deny check
cargo audit
cargo publish --dry-run
```

All green. Counts at this tag (identical for every feature combination):

- 39 unit + 32 integration + 5 property + 105 doctests, with the property
  tests also soaked at 20,000 cases each.

Benchmark baselines (x86_64, release profile; each edit figure is two edits —
a keystroke and its undo — on generated JSON unless noted):

| Benchmark | Windows | Linux (WSL2) |
|---|---:|---:|
| `edit/10KB` | ~1.3 µs | ~0.76 µs |
| `edit/100KB` | ~2.2 µs | ~1.2 µs |
| `edit/1MB` | ~11 µs | ~7.0 µs |
| `edit_full/1MB` (two full reparses) | ~41 ms | ~21 ms |
| `edit_flat/1MB` (7,700-element array) | ~32 µs | ~25 µs |
| `edit_deep/40000` (40,000-deep chain) | ~0.90 ms | ~0.58 ms |
| `parse/1MB` | ~21 ms | ~9.0 ms |
| `snapshot/clone` | ~14 ns | ~13 ns |
